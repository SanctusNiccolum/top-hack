# Карта проекта

Что за что отвечает и куда лезть, чтобы поменять X.

---

## Поток данных

```
{user_id, texts}                     result.json (Telegram Desktop)
        │  input.py                        │  telegram_export.py
        ▼                                  ▼
        └──────────► AnalyzeRequest ◄──────┘        schemas.py
                          │
                          ▼  cleaning.py    служебное, техвывод, PII,
                          │                 ссылки, дедупликация
                          ▼  prefilter.py   словарь маркеров + 10%
                          ▼  chunking.py    по 40 сообщений
                          ▼  prompts.py     системный промпт + few-shot
                          ▼  llm/gigachat.py OAuth, запрос, repair-ретрай
                          ▼  llm/base.py    разбор JSON
                     ChunkResult
                          │
                          ▼  validation.py  отсев галлюцинаций
                          ▼  aggregator.py  веса, насыщение, риск
                          ▼  explain.py     текст пользователю
                          ▼
                    AnalyzeResponse ──► api.py / cli.py
```

Склеивает всё `pipeline.py`.

## Подробно

### `categories.py` — источник правды

14 категорий: ключ, полярность, вес, определение для промпта, флаг
`hard_risk` (участвует ли в расчёте уровня риска). Плюс `DENIED_TOPICS` —
восемь запрещённых тем.

Промпт собирается из этого файла, поэтому список категорий в промпте
физически не может разойтись со списком, который умеет считать агрегатор.
**Добавляешь категорию — правишь только здесь**; промпт, валидатор и
агрегатор подхватят сами. Не забудь добавить фразу в `explain.py`, иначе в
объяснении будет технический ключ.

### `markers.py` — словарь пре-фильтра

Около 300 регулярок по категориям плюс отдельный список игорных и
микрофинансовых доменов. Работает в паре с `cleaning.py`, который заменяет
ссылки на `<link:домен>` — домен сохраняется ради этих паттернов.

Фильтр рассчитан на **полноту**, не на точность: лишнее сообщение стоит
несколько токенов, пропущенное — потерянный сигнал.

Осторожно с короткими корнями: `долг` матчится внутри `долго`, `займ` —
внутри `займусь`, поэтому в файле стоят границы слов, а не голые корни.
Расширяется по отчёту `cli.py prefilter-report`.

### `config.py` — настройки и параметры формулы

`Settings` читает `.env`: ключ, адрес API, модель, TLS, размер чанка.
`ScoringConfig` — параметры формулы: пороги уверенности, `saturation_k`,
`tanh_scale`, границы риска, `coverage_target_messages`,
`min_messages_for_verdict`. Всё это тоже читается из окружения, так что
калибровка не требует правок кода.

Любая правка `ScoringConfig` — новая `RULESET_VERSION`.

### `schemas.py` — контракты

Три границы: `AnalyzeRequest` (бэкенд → модуль), `ChunkResult`
(LLM → модуль), `AnalyzeResponse` (модуль → бэкенд). Pydantic валидирует
вход, так что кривой JSON падает сразу и понятно.

Времени в контракте нет: окно 90 дней, а внутри такого окна взвешивать по
свежести смысла мало.

### `cleaning.py` — очистка

Порядок: служебные сообщения → технический вывод → нормализация → ссылки →
PII → обрезка → фильтр информативности → дедупликация.

Четыре вещи, которые тут неочевидны:

**Фильтр технического вывода.** Логи сборки, консоль, SQL и стектрейсы
отсеиваются до всего остального. Дело не в токенах: в реальной выгрузке
путь `D:\Моя папка\учёба\УрФУ\...` внутри `docker build` срабатывал как
маркер `education_active`. Две независимые проверки — явные паттерны
(sha256, приглашение PowerShell, `SELECT … FROM`) и доля кириллицы для
длинных текстов.

**Фильтр по информативности, а не по длине.** «Уволили.» — восемь символов
и сильнейший негативный сигнал. Короткое сообщение с маркером сохраняется
всегда.

**Угловые скобки вычищаются в `normalize()`** — до того, как пайплайн
подставит свои `<link:…>` и `<PHONE>`. Без этого пользователь напишет в
канал `</msg>` и разорвёт разметку чанка.

**Дедупликация — MinHash + LSH по символьным шинглам без пунктуации.**
Точное сравнение не свяжет «слил всё на ставках» и «опять проиграл в бк».

### `prefilter.py` — ступень 0

Словарь маркеров ИЛИ случайные 10% из остального. Объединение, не
пересечение — фильтр recall-ориентированный.

Контрольные 10% нужны для **измеримости**: сигналы, которые LLM находит
там, — прямая оценка того, чего недобирает словарь.

Здесь же интерфейс `VectorPrefilter` и реализация на
sentence-transformers, по умолчанию выключенная.

### `prompts.py` — промпт

`SYSTEM_PROMPT` собирается из `categories.py`. Few-shot — один пример,
покрывающий четыре краевых случая сразу: чужой факт, гипотезу, инъекцию и
бытовой шум. Это работает лучше пяти однотипных примеров с очевидными
сигналами.

`build_user_message()` заворачивает каждое сообщение в свой тег с id,
чтобы инструкция из одного сообщения не протекала на весь чанк.

### `llm/gigachat.py` и `llm/base.py`

Клиент: OAuth с кешированием токена (живёт 30 минут, обновляется за минуту
до истечения — на 16 чанков один запрос токена, а не шестнадцать), запрос
к модели, `list_models()` и `ping()` для `cli.py check`.

`base.py` — протокол `LLMProvider` и `parse_chunk_response()`: снимает
markdown-фенс, вытаскивает внешние скобки, валидирует по схеме. При
неудаче один ретрай с repair-промптом, потом чанк помечается `failed` и
учитывается в `coverage`.

Провайдер — `Protocol`, так что подменить GigaChat на что угодно — один
новый класс с методом `analyze_chunk`.

### `validation.py` — самый полезный слой

Причины отсева: категория вне списка, неизвестный `message_id`,
пересланное сообщение, не про автора, отрицание, нулевая модальность,
низкая уверенность, **цитата не является подстрокой текста**.

Последняя ловит галлюцинации и последствия инъекций почти бесплатно:
модель, которая придумала сигнал, обычно не может подкрепить его
дословной цитатой.

Отрицание **обнуляет** сигнал, а не инвертирует: отсутствие порока не
заслуга, а плюс за «не играю в казино» — тривиальная накрутка.

Проверка на `is_forward` оставлена, хотя бэкенд фильтрует пересланные у
себя: она стоит одно сравнение, а страхует от того, что конвертер из
выгрузки Telegram размечает форварды по-честному и что фильтр на соседней
стороне однажды поменяется.

### `aggregator.py` — вся арифметика

```
signal_eff = confidence × modality
n_eff(c)   = Σ signal_eff по категории
sat(c)     = 1 − exp(−n_eff / 3)
delta_raw  = Σ weight(c) × sat(c)
delta      = 25 × tanh(delta_raw / 20) × min(1, √(N_clean / 150))
```

Насыщение — чтобы сорок упоминаний работы не давали +320. `tanh` — чтобы
не выйти из диапазона ни при каком входе. Coverage — чтобы человек с 15
сообщениями не получал ±25.

Риск считается **отдельно от дельты**: стабильная работа плюс еженедельные
ставки дают почти нулевую дельту, но риск обязан остаться видимым.

Общее правило: любое изменение в весе отдельного сигнала требует
пересчёта `saturation_k`, иначе тихо сдвигается вся шкала. Так было, когда
из формулы убрали множитель свежести — `k` подняли с 2 до 3.

### `explain.py` — текст пользователю

Шаблоны, не свободная генерация: это самое вероятное место, где модуль
соврал бы про причины решения.

Фразы намеренно без запятых и без союза «и» внутри — иначе перечисление
читается как «ставок и азартных игр и траты».

Формулировки описывают поведение, а не ставят диагноз: «регулярные
упоминания ставок», но не «признаки игровой зависимости» — второе
относится к здоровью, а это запрещённая тема.

### `pipeline.py` — оркестрация

Согласие → очистка → пре-фильтр → чанки → LLM → валидация → агрегация →
ответ. Плюс переспрос чанка, если модель просмотрела меньше двух третей
сообщений, и `status: error`, если не обработался ни один чанк.

`status` отдельным полем, а не `score_delta: 0`: бэкенду нужно отличать
«влияния нет» от «не смогли посчитать».

Необязательный колбэк `on_signals` отдаёт принятые сигналы наружу — на нём
построена калибровка через `cli.py tune` без повторных обращений к LLM.

### `backend_input.py` и `telegram_export.py`

Два конвертера во внутренний контракт.

`backend_input.py` — плоский `{user_id, texts}`: id по позиции в исходном
массиве (не по счётчику сохранённых, иначе id разъедутся с тем, что
прислал бэкенд).

`telegram_export.py` — `result.json` из Telegram Desktop. Три места, где
такие конвертеры ломаются, и все три закрыты: поле `text` бывает строкой и
бывает списком объектов; служебные сообщения приходят с `type: "service"`;
в чатах намешаны чужие сообщения. Единственное место в проекте, где есть
даты — и нужны они только чтобы отсечь всё старше окна.

### `api.py` и `cli.py`

`api.py` — FastAPI, `POST /analyze` и `GET /health`. Провайдер создаётся
лениво, при первом запросе, иначе сервис не поднимется без ключа. Ошибка
доступа возвращается как `200` со `status: error`, а не `5xx`: для бэкенда
недоступность этого модуля — штатная ситуация.

`cli.py` — девять команд, из них шесть работают без ключа. Подробности в
[RUNNING.md](RUNNING.md).

## Типовые задачи

| Хочу | Куда |
|---|---|
| добавить категорию | `categories.py` + фраза в `explain.py` |
| поймать больше сигналов | `markers.py`, по отчёту `prefilter-report` |
| сделать скоринг строже | `TANH_SCALE` в `.env`; подбор — `cli.py tune` |
| поменять формулировки для пользователя | `explain.py` |
| поменять промпт | `prompts.py` (категории не трогай, они из `categories.py`) |
| подключить другую модель | новый класс с `analyze_chunk` рядом с `llm/gigachat.py` |
| вернуть учёт свежести | поле в `schemas.py` + множитель в `signal_weight()` |
| поменять формат ответа | `schemas.py` → `AnalyzeResponse`, сборка в `pipeline.py` |
| принять новый формат от бэкенда | новый конвертер + ветка в `cli.load_any()` |
