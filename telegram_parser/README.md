# Telegram-парсер (Telethon userbot + режим импорта)

Backend-компонент для кейса «Альтернативный скоринг» (УрФУ × Сбер). Собирает
данные из Telegram-аккаунта пользователя (с его согласия) для последующего
ИИ-анализа. Полный контекст решений — в `telegram_parser_plan.md`.

## Два режима — и почему их два

**`main.py` (live, через Telethon)** — основной рабочий путь. Live-подключение
к Telegram по `session_string`, требует `api_id`/`api_hash` с
my.telegram.org. Изначально это было заблокировано для российских номеров
(антифрод my.telegram.org режет регистрацию при VPN, а без VPN сайт в
России не открывается вообще) — обходится через `hosts`-файл, направляющий
`my.telegram.org` напрямую на IP Telegram в обход DNS-блокировки, без VPN.

**`main_import.py` (импорт, без Telegram API)** — резервный путь на случай,
если обход DNS-блокировки не подойдёт кому-то ещё в команде. Читает
`result.json` — официальный экспорт Telegram Desktop (Settings → Advanced
→ Export Telegram Data). Пишет в те же таблицы, той же логикой.
**Чем хуже live-режима:** в экспорте нет `username`/`about` у чатов —
сверка подписок с `trusted_channels` невозможна, оба поля всегда NULL.

## Ключевая модель: без ручной классификации чата

Для каждого `chat_id` парсер **всегда пробует оба метода** — извлечь свои
сообщения (`from_id == me`) И метаданные подписки (title/username/about).
Что применимо к этой сущности, то и попадёт в БД; что нет — просто
останется пустым. Раньше был явный флаг `type: own_messages|subscription`,
который приходилось выставлять вручную (в т.ч. в dev-инструментах) — из-за
этого приватные группы/каналы, где пользователь формально «подписчик», но
реально пишет сам, ошибочно классифицировались и терялись. Метод отбора не
нужен: сообщения фильтруются по авторству (`sender_id == me`) независимо
от типа чата, а метаданные подписки просто не находятся там, где их нет
(например, у личных чатов).

## user_id — всегда реальный Telegram ID, не то, что передал вызывающий код

И в live-, и в импорт-режиме `user_id` **не принимается на вход** —
берётся из самого источника данных:
- live: `me.id` после `client.get_me()` (реальный аккаунт, который только
  что залогинился)
- импорт: `personal_information.user_id` из самого экспорта

Раньше `user_id` передавался в payload и в dev-инструментах по умолчанию
подставлялось `1` для любого теста — это создавало риск тихо перемешать
данные разных людей под одним и тем же идентификатором. Теперь такой
подмены попросту не может произойти: единственный источник правды —
сам Telegram-аккаунт.

## PII-очистка — без фильтра по длине сообщения

`cleaning.py` вырезает телефоны/email/`@упоминания` из текста, но **больше
не отбрасывает короткие сообщения** ("ок", "да", "хз" и т.п.) — раньше
фильтр по минимальной длине (4 слова) убирал их как "шум", сейчас любое
сообщение самого пользователя сохраняется как есть (после PII-очистки).

## Экспорт для ИИ — отдельным шагом из БД

Хранение остаётся в Postgres как и было (`messages`/`subscriptions`/
`parse_state`/`ai_queue`), но для передачи в ИИ-сервис есть отдельный
плоский формат:

```bash
DATABASE_URL="postgresql://..." python -m telegram_parser.export_texts <user_id>
```

> **Про запуск.** Отдельного docker-стека у парсера больше нет: он поднимал
> собственный Postgres на том же порту 5432 и конфликтовал с основным.
> Парсер живёт в образе бэкенда и запускается подпроцессом — см.
> `backend/app/telegram_analysis/runner.py`. Поднимается всё одной командой
> `docker compose up` из корня репозитория; таблицы создаёт alembic.
> Дев-скрипты в `dev_tools/`, зовущие `docker compose run parser`,
> устарели — рабочий путь теперь через API (`/telegram/login/*`,
> `/telegram/analyze`).

Печатает в stdout:
```json
{
  "user_id": 5270187642,
  "texts": ["текст сообщения 1", "текст сообщения 2", "..."]
}
```

Только тексты сообщений (без даты/`is_forward`/`is_reply`/подписок) — это
самый простой вид, к которому явно попросили привести вывод. Если позже
понадобятся дата/флаги/подписки в этом же экспорте — база данных всё это
уже хранит, `export_texts.py` просто пока выбирает только `text`.

## Про вход по юзернейму вместо номера — невозможно физически

Проверено: Telegram привязывает вход строго к номеру телефона на уровне
самого протокола — ни `send_code_request`, ни `sign_in`, ни `start` не
поддерживают отправку кода на `@username` ни в одной версии Telethon, это
не ограничение библиотеки. Единственная официальная альтернатива ручному
вводу номера — QR-код (`client.qr_login()`), но он тоже привязан к тому же
номеру, просто другой способ подтверждения. Не реализовано (не требовалось
после того, как вход по номеру заработал) — скажите, если нужен как
альтернативный UX.

## Установка

```bash
pip install -r requirements.txt
psql "$DATABASE_URL" -f schema.sql   # один раз, создаёт таблицы
```

## Docker

**Продовый путь: парсер живёт в одном образе с `api`** — весь проект
(фронт, бэк, ИИ-апи) по одному контейнеру на сервис, парсер не отдельный
сервис, а часть бэкенда:

```dockerfile
COPY telegram_parser/ ./telegram_parser/
RUN pip install --no-cache-dir -r telegram_parser/requirements.txt
```

Вызывается обычным OS-подпроцессом внутри уже работающего контейнера
`api`, никакого Docker socket/DinD не нужно:

```python
proc = await asyncio.create_subprocess_exec(
    sys.executable, "-m", "telegram_parser.main",
    stdin=asyncio.subprocess.PIPE,
    env={**os.environ, "DATABASE_URL": ...},
)
proc.stdin.write(json.dumps(payload).encode())
await proc.stdin.drain()
proc.stdin.close()
# fire-and-forget: НЕ await proc.wait() — статус смотрим в parse_state
```

**`Dockerfile`/`docker-compose.yml` в этой директории — не для прода**, а
для локальной проверки пакета изолированно:

```bash
docker compose up -d postgres        # схема накатится автоматически
docker compose build parser
```

## Запуск — live-режим (main.py)

Вход на **stdin** (не argv/env/файл — `session_string` даёт полный доступ
к аккаунту, а argv/env видны другим процессам через `ps aux`/`/proc`):

```json
{
  "session_string": "...",
  "api_id": 12345,
  "api_hash": "...",
  "chat_ids": [-100111111111, 5270187642, -100222222222]
}
```

Для ручного теста проще не собирать JSON руками, а использовать
`dev_tools/run_test.py` — логин (номер+код, `api_id`/`api_hash` из
`TG_API_ID`/`TG_API_HASH`), список чатов, ввод `chat_id` в консоли, запуск
через `docker compose run` и проверку в БД, всё сразу:

```bash
python dev_tools/run_test.py
```

`api` вызывает `main.py` как **fire-and-forget** — не дожидается
завершения. Статус/ошибки — в `parse_state` (по каждому чату отдельно),
готовность для ИИ — в `ai_queue`.

## Запуск — импорт-режим (main_import.py)

```json
{
  "export_path": "/path/to/result.json",
  "chat_ids": [111111111, 222222222]
}
```

```bash
python dev_tools/list_chats_from_export.py /path/to/result.json  # найти chat_id
echo '{...}' | DATABASE_URL="postgresql://..." python -m telegram_parser.main_import
```

## Структура

```
telegram_parser/
  main.py               # live-режим: stdin -> Telethon -> Postgres
  telegram_client.py    # Telethon-логика: свои сообщения, метаданные подписок
  main_import.py        # импорт-режим (резерв): result.json -> Postgres
  import_parser.py      # разбор формата экспорта Telegram Desktop
  export_texts.py        # экспорт текстов пользователя из Postgres в плоский JSON для ИИ
  cleaning.py            # PII-очистка (общая для обоих режимов)
  db.py                  # весь SQL (asyncpg, общий для обоих режимов)
schema.sql               # DDL: messages, subscriptions, trusted_channels, parse_state, ai_queue
tests/                   # unittest + фейковые telethon/asyncpg, без внешних зависимостей
dev_tools/               # НЕ часть парсера — вспомогательные скрипты для теста/отладки
  run_test.py              # live: логин + список чатов + выбор в консоли + запуск + проверка
  get_session.py           # live: только интерактивный логин, печатает session_string
  list_chats.py            # live: только список диалогов аккаунта с их chat_id
  list_chats_from_export.py  # импорт: список чатов из локального result.json
  fake_run.py              # прогон реальной логики на фейковых данных, без Telegram вообще
```

## Тесты

```bash
python -m unittest discover -s tests -v
```

37 тестов, без реального Telegram/Postgres — `tests/_stubs` содержит
фейковые `telethon`/`asyncpg`, управляемые сценарием. Покрыто: обе
выборки (сообщения + подписка) всегда пробуются на каждый chat_id,
`user_id` берётся из `me.id`/экспорта а не из входных данных, короткие
сообщения больше не фильтруются, изоляция ошибок одного чата, повтор при
`FloodWaitError`, прогрев кэша сущностей через `get_dialogs()`, PII-очистка
(email, короткие числовые ID/даты не считаются телефоном).

## Ключевые решения (кратко, подробности в plan.md)

- Все сообщения самого пользователя (`from_id == me`) сохраняются как
  есть, включая короткие и пересланные (с флагом `is_forward`)
- Глубина — 3 месяца, инкрементально от `parse_state.last_parsed_at`
- PII (телефоны, `@упоминания`, email) вырезаются **до** записи в БД
- Оба метода (сообщения + подписка) пробуются на каждый `chat_id` — без
  ручной классификации
- `user_id` — реальный Telegram ID (`me.id`/экспорт), не входной параметр
- Подписки сверяются с `trusted_channels` по `username`, не по `title`
- Связь с ИИ-сервисом — через БД (`ai_queue` + отдельный экспорт
  `export_texts.py`), без прямого вызова
- Сессия одноразовая: `log_out()` в конце любого запуска

## Известные ограничения MVP

- Регэксп для телефонов — эвристика: голые цифры без разделителей
  считаются телефоном только от 10 цифр (чтобы не путать с датами/
  номерами заказов), с разделителями — вырезаются как раньше
- Не проверено на реальном broadcast-канале, где пользователь сам пишет
  (не просто читает) — стоит подтвердить на живом примере
- `trusted_channels` пока пустая таблица — наполнение за командой
- `export_texts.py` отдаёт только `text` — без даты/флагов/подписок; в БД
  всё это есть, при необходимости легко расширить формат вывода
