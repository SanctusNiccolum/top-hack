# Telegram-парсер (Telethon userbot + режим импорта)

Backend-компонент для кейса «Альтернативный скоринг» (УрФУ × Сбер). Собирает
данные из Telegram-аккаунта пользователя (с его согласия) для последующего
ИИ-анализа. Полный контекст решений — в `telegram_parser_plan.md`.

## Два режима — и почему их два

**`main.py` (live, через Telethon)** — основной рабочий путь. Live-подключение
к Telegram по `session_string`, требует `api_id`/`api_hash` с
my.telegram.org. Изначально это было заблокировано для российских номеров
(антифрод my.telegram.org режет регистрацию при VPN, а без VPN сайт в
России не открывается вообще) — обходится через `hosts`-файл, направляющий
`my.telegram.org` напрямую на IP Telegram в обход DNS-блокировки, без VPN
(тогда IP запроса остаётся российским, антифрод не срабатывает). После
этого live-режим работает и активно используется для теста.

**`main_import.py` (импорт, без Telegram API)** — резервный путь на случай,
если обход DNS-блокировки не подойдёт (например, у провайдера блокировка
глубже, на уровне DPI, не только DNS) или понадобится кому-то ещё в
команде без своего api_id/api_hash. Вместо live-подключения читает
`result.json` — официальный экспорт Telegram Desktop (Settings → Advanced
→ Export Telegram Data). Не требует НИ api_id/api_hash, НИ my.telegram.org,
НИ даже сети до Telegram — только уже выгруженный пользователем файл.
Пишет в те же таблицы (`messages`/`subscriptions`/`parse_state`/`ai_queue`),
той же логикой PII-очистки и фильтра коротких сообщений.

**Чем импорт хуже live-режима** — у объекта чата в экспорте нет полей
`username`/`about`, поэтому для `subscriptions` сверка с
`trusted_channels` физически невозможна: `username`/`about` всегда NULL,
`trusted_channel_id` всегда NULL. Это ограничение формата экспорта, не
баг реализации.

## Установка

```bash
pip install -r requirements.txt
psql "$DATABASE_URL" -f schema.sql   # один раз, создаёт таблицы
```

## Docker

**Продовый путь: парсер живёт в одном образе с `api`**, отдельного
контейнера у него нет (весь проект — фронт, бэк, ИИ-апи — по одному
контейнеру на сервис; парсер не «ещё один сервис», а часть бэкенда). В
`Dockerfile` бэкенда добавляете:

```dockerfile
COPY telegram_parser/ ./telegram_parser/
RUN pip install --no-cache-dir -r telegram_parser/requirements.txt
```

и вызываете точно так же, как на голом хосте — обычным OS-подпроцессом
внутри уже работающего контейнера `api`, никакого Docker socket/DinD не
нужно:

```python
proc = await asyncio.create_subprocess_exec(
    sys.executable, "-m", "telegram_parser.main",
    stdin=asyncio.subprocess.PIPE,
    env={**os.environ, "DATABASE_URL": ...},
)
proc.stdin.write(json.dumps(payload).encode())
await proc.stdin.drain()
proc.stdin.close()
# fire-and-forget: дальше НЕ await proc.wait() — просто не ждём, статус в parse_state
```

Контейнеру `api` в любом случае нужен исходящий доступ в интернет (до
серверов Telegram), это уже требование не к парсеру, а к сетевым правилам
контейнера в целом.

**`Dockerfile`/`docker-compose.yml` в этой директории — не для прода**, а
чтобы гонять и проверять сам пакет изолированно (например, воспроизвести
баг без поднятия всего остального стека):

```bash
docker compose up -d postgres        # поднять Postgres, схема накатится автоматически
docker compose build parser
echo '{...}' | docker compose run --rm -T parser   # -T обязателен: без него
                                                     # Docker выделяет псевдо-TTY
                                                     # и обычный pipe в stdin ломается
```

## Запуск — live-режим (main.py, требует api_id/api_hash)

Это **не** импортируемый модуль, а самостоятельный подпроцесс. `api`
запускает его и передаёт входные данные через **stdin** (не argv/env/файл —
внутри `session_string`, полный доступ к Telegram-аккаунту пользователя, а
argv/env видны другим процессам на машине через `ps aux`/`/proc`, файл же
оставляет секрет на диске).

Для ручного теста проще всего не собирать JSON руками, а использовать
`dev_tools/run_test.py` — один скрипт делает всё: логин (только номер+код,
`api_id`/`api_hash` из переменных окружения `TG_API_ID`/`TG_API_HASH`,
задать один раз), список ваших чатов, ввод нужных `chat_id` в консоли,
запуск `docker compose run` и проверку результата в БД:

```bash
python dev_tools/run_test.py
```

Формат входа на stdin (то, что `run_test.py` собирает автоматически):

```bash
echo '{
  "user_id": 123,
  "session_string": "...",
  "api_id": 12345,
  "api_hash": "...",
  "chats": [
    {"chat_id": -100111111111, "type": "own_messages"},
    {"chat_id": -100222222222, "type": "subscription"}
  ]
}' | DATABASE_URL="postgresql://user:pass@host:5432/dbname" python -m telegram_parser.main
```

`api` вызывает это как **fire-and-forget** — не дожидается завершения
процесса. Статус и ошибки смотрите в таблице `parse_state` (по каждому чату
отдельно), готовность данных для ИИ — в `ai_queue`.

## Запуск — импорт-режим (main_import.py, без Telegram API)

Сейчас основной рабочий путь. Вход — тоже JSON на stdin, но вместо
`session_string`/`api_id`/`api_hash` нужен путь к уже выгруженному
`result.json` (см. выше про Export Telegram Data) и список `chat_id` из
этого файла, которые пользователь разрешил использовать — типы
(`own_messages`/`subscription`) определяются автоматически по `type` в
самом экспорте, вручную указывать не нужно.

Сначала найдите нужные `chat_id` в своём экспорте:

```bash
python dev_tools/list_chats_from_export.py /path/to/result.json
```

Затем запустите импорт:

```bash
echo '{
  "user_id": 123,
  "export_path": "/path/to/result.json",
  "chat_ids": [111111111, 222222222]
}' | DATABASE_URL="postgresql://user:pass@host:5432/dbname" python -m telegram_parser.main_import
```

`export_path` должен быть доступен процессу — в Docker это обычный volume
с файлом экспорта, ничего специфичного для контейнеризации тут нет (даже
проще live-режима: не нужен сетевой доступ до Telegram вообще).

## Структура

```
telegram_parser/
  main.py               # live-режим: чтение stdin, оркестрация по чатам через Telethon
  telegram_client.py    # Telethon-логика: свои сообщения, метаданные подписок
  main_import.py        # импорт-режим (резерв): чтение result.json вместо live-Telegram
  import_parser.py      # разбор формата экспорта Telegram Desktop
  cleaning.py           # PII-очистка + фильтр коротких сообщений (общий для обоих режимов)
  db.py                 # весь SQL (asyncpg, общий для обоих режимов)
schema.sql               # DDL: messages, subscriptions, trusted_channels, parse_state, ai_queue
tests/                   # unittest + фейковые telethon/asyncpg, без внешних зависимостей
dev_tools/               # НЕ часть парсера — вспомогательные скрипты для теста/отладки
  run_test.py              # live: логин + список чатов + выбор в консоли + запуск + проверка, всё сразу
  get_session.py           # live: только интерактивный логин, печатает session_string
  list_chats.py            # live: только список диалогов аккаунта с их chat_id
  list_chats_from_export.py  # импорт: список чатов из локального result.json
  fake_run.py              # прогон реальной логики на фейковых данных, без Telegram вообще
```

## Тесты

```bash
python -m unittest discover -s tests -v
```

37 тестов, не требуют реального Telegram-аккаунта или Postgres —
`tests/_stubs` содержит фейковые `telethon`/`asyncpg`, управляемые
сценарием. Покрыто: фильтрация чужих сообщений, флаг `is_forward`, сверка
подписки с `trusted_channels`, изоляция ошибок одного чата от остальных,
повтор при `FloodWaitError`, отказ при неавторизованной сессии,
регрессионные тесты на PII-очистку (email, короткие числовые ID/даты),
прогрев кэша сущностей через `get_dialogs()` (см. ниже), и отдельно —
весь импорт-режим (`import_parser.py`/`main_import.py`) на синтетическом
`result.json`.

## Ключевые решения (кратко, подробности в plan.md)

- Только сообщения самого пользователя (`from_id == me`), включая им же
  пересланные — с флагом `is_forward`, чтобы ИИ отличал свои слова от чужих
- Глубина — 3 месяца, инкрементально от `parse_state.last_parsed_at`
- PII (телефоны, `@упоминания`) вырезаются **до** записи в БД
- Сообщения короче 4 слов отбрасываются как шум
- Подписки сверяются с `trusted_channels` по `username`, не по `title`
  (заголовок канала можно менять как угодно, юзернейм — нет)
- Связь с будущим ИИ-сервисом — только через БД (`ai_queue`), без прямого
  вызова

## Известные ограничения MVP

- Регэксп для телефонов — эвристика, не строгий парсер номеров. Голые
  цифровые последовательности без разделителей (пробел/дефис/скобки)
  считаются телефоном только от 10 цифр — это исключает частые
  ложные срабатывания на датах (ДДММГГГГ) и номерах заказов, но короткие
  телефоны без форматирования короче 10 цифр (не РФ-формат) всё ещё могут
  проскочить. Числа с разделителями и явные РФ-номера (`+7`/`8` + 10 цифр)
  вырезаются как раньше
- Email-адреса теперь вырезаются целиком отдельным regex'ом до сверки с
  `@упоминаниями` — раньше от email оставался мусорный обрубок вида
  `test.ru` (страдала только доменная часть после `@`)
- Реальный тест против живого Telegram-аккаунта уже проводился (через
  Docker, с настоящим `session_string`) — именно так нашёлся и был
  исправлен баг с `get_dialogs()` выше. Дальнейшее тестирование по мере
  использования только приветствуется
- **Исправлено:** `StringSession`, в отличие от файловой SQLite-сессии,
  не хранит кэш "уже виденных" сущностей — каждый новый процесс парсера
  стартовал с пустым кэшем, и `get_entity()` по голому числовому ID
  личного чата падал с `Could not find the input entity` (Telethon
  требует сначала "встретить" сущность в рамках текущего процесса,
  обычно через `get_dialogs()`). Поймано на реальном тесте через Docker.
  Фикс — `client.get_dialogs()` один раз в начале `main()`, до цикла по
  чатам. См. официальную документацию Telethon про entities.
- Не проверено на реальном broadcast-канале: `sender_id == me_id`
  надёжно отличает "свои" сообщения в ЛС/группах, но для постов в
  собственном канале Telegram может атрибутировать сообщение самому
  каналу, а не автору (особенно с анонимными админами) — стоит
  подтвердить на живом канале, что подписка `own_messages` там вообще
  что-то улавливает
- `client.log_out()` в `finally` отзывает сессию при ЛЮБОМ завершении
  процесса — это **ожидаемое поведение по дизайну**, а не баг: продуктовое
  решение было именно "одноразовая сессия" (см. plan.md). Это совместимо
  с инкрементальностью через `parse_state.last_parsed_at` ровно потому,
  что "инкрементально" здесь относится к **сообщениям**, а не к сессии —
  предполагается, что при следующем обращении пользователь заново
  проходит логин (номер+код) и получает НОВЫЙ `session_string`; старый к
  этому моменту уже не нужен. Из этого следует неявное требование к
  компоненту логина: он обязан каждый раз запрашивать свежий вход, а не
  кэшировать/переиспользовать `session_string` между запусками парсера —
  если это не так, планы по инкрементальности стоит пересмотреть
- `trusted_channels` пока пустая — наполнение списком ссылок за командой
