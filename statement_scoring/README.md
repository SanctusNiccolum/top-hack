# Скоринг по банковской выписке

Модуль реализует одну ветку общего пайплайна скоринга:

```
Выписка карты (3 мес) → Feature Engineering → CatBoost Model → скор (0–25) + объяснение
```

Ветки «Анкетирование» и «Telegram → RuBERT/NER → LLM-коррекция» считаются
отдельно и в этот модуль не входят — их скоры объединяются с результатом
этого модуля на более позднем этапе (например, взвешенной суммой или
отдельной моделью-стекером).

## Архитектура

```
PDF-выписка
   │
   ▼
parser.py         — построчно извлекает операции (дата/время/категория/
   │                 сумма, дата обработки/код/описание), определяет
   │                 направление операции по знаку суммы, сверяет
   │                 контрольные суммы с итогами банка в шапке выписки.
   ▼
features.py       — 22 признака в 5 блоках: доход, расходы, денежный
   │                 поток, долговая нагрузка, риск-флаги.
   ▼
scoring_rules.py  — расчёт скора по формуле База × K_итог (см. ниже).
   │                 Используется и как самостоятельный результат, и
   │                 как источник разметки для обучения модели.
   ▼
train_model.py    — обучает CatBoostRegressor (или sklearn-фолбэк, если
   │                 catboost не установлен) предсказывать тот же скор
   │                 по признакам напрямую, без пересчёта формулы.
   ▼
score.py          — точка входа: PDF → операции → признаки → скор
                     модели + скор по формуле → объяснение → отчёт.
```

## Формула скора (`scoring_rules.py`)

Расчёт устроен так же, как в анкетной ветке скоринга — трёхслойная
модель «доход → база по ПДН → корректирующие коэффициенты», только на
вход идут не ответы анкеты, а признаки, извлечённые из выписки:

```
Слой 1 (доход):
    Дч_скорр = avg_monthly_income × K_доход

Слой 2 (база):
    ПДН = estimated_monthly_debt_payment / Дч_скорр × 100
    База = clamp(100 − ПДН, 0, 100)

Слой 3 (надёжность):
    K_итог = K_регулярность × K_кредитная_история × K_структура_счёта
             × K_сбережения × K_разнообразие_трат

Итог:
    Скор = clamp(База × K_итог × 0.25, 0, 25)
```

База и ПДН считаются в процентах (0–100), как и положено ПДН — в
шкалу 0–25 переводится только финальное число, последним шагом
(× 0.25).

Часть коэффициентов Слоя 3 — прямые аналоги вопросов анкеты, взятые с
теми же значениями, потому что вопрос анкеты и признак выписки меряют
одно и то же с разных сторон:

| Коэффициент | Признак выписки | Аналог в анкете | Значения |
|---|---|---|---|
| Подтверждаемость источника дохода (Слой 1) | `cash_deposit_share` | «Источник дохода» + «НПД-статус» | 1.00 / 0.97 / 0.90 / 0.80 |
| Регулярность дохода | `income_cv` | «Регулярность дохода» | 1.10 / 1.08 / 0.90 / 0.80 / 0.50 |
| Кредитная история и риск | `risk_tx_count`, `risk_amount_share`, `debt_series_count` | «Кредитная история» + «Просрочки» | 1.05 / 0.95 / 0.80 / 0.65 |
| Разнообразие трат | `category_entropy` | «Подписки» | 1.05 / 1.00 / 0.95 |

Два коэффициента введены отдельно — соответствующего вопроса в анкете
нет и быть не может, эти признаки видны только по факту движений по
счёту:

| Коэффициент | Признак выписки | Смысл |
|---|---|---|
| Концентрация оборота | `large_expense_share`, `max_income_share`, `round_amount_share` | Почти весь оборот формируют одна-две крупные операции — похоже на транзитный счёт, а не на обычное потребление |
| Норма сбережений | `savings_rate` | Доля дохода, остающаяся после расходов |

`ПДН` считается напрямую по данным выписки: `estimated_monthly_debt_payment`
находится автоматически — поиском серий регулярных исходящих платежей
похожего размера одному контрагенту (банку/МФО). Это тот параметр,
который анкета не может получить без отдельного вопроса, а выписка
даёт сама.

## Признаки (`features.py`)

| Блок | Признак | Смысл |
|---|---|---|
| Доход | `avg_monthly_income` | Средний доход в месяц за период выписки |
| | `income_tx_count` | Число операций пополнения |
| | `income_cv` | Коэффициент вариации дохода по месяцам |
| | `income_gap_std_days` | Разброс интервалов между поступлениями |
| | `cash_deposit_share` | Доля дохода в виде внесения наличных |
| | `max_income_share` | Доля крупнейшего поступления в общем доходе |
| Расходы | `avg_monthly_expense` | Средние траты в месяц |
| | `expense_tx_count` | Число расходных операций |
| | `category_entropy` | Энтропия Шеннона по категориям трат |
| | `essential_share` / `discretionary_share` | Доля обязательных / необязательных категорий |
| | `large_expense_share` | Доля расходов на аномально крупные операции |
| Денежный поток | `savings_rate` | (доход − расход) / доход |
| | `expense_income_ratio` | расход / доход |
| | `balance_volatility` | Волатильность дневного изменения остатка |
| Долговая нагрузка | `estimated_monthly_debt_payment` | Автоматически найденные регулярные платежи, похожие на погашение кредита/займа |
| | `estimated_dti` | estimated_monthly_debt_payment / avg_monthly_income |
| | `debt_series_count` | Число найденных таких серий платежей |
| Риск | `risk_tx_count` / `risk_amount_share` | Операции с признаками МФО/ставок/казино/крипты |
| | `round_amount_share` | Доля «круглых» сумм (кратны 1000) |
| Контекст | `tx_per_month`, `period_days` | Активность счёта, длина периода |

## Обучение модели (`train_model.py`)

Исторических пар «признаки → фактический исход по кредиту» пока нет,
поэтому первая версия модели обучается на данных, размеченных формулой
из `scoring_rules.py`: `synth_data.py` сэмплирует признаки для шести
архетипов держателя счёта (стабильная зарплата, нерегулярный фриланс,
студент, закредитованность, риск-операции, транзитный счёт) и
размечает их той же формулой с шумом. Модель учится обобщать формулу
на комбинации признаков, которых не было ни в одном архетипе явно.

Когда появятся реальные наблюдаемые исходы (например, факт погашения
или просрочки через N месяцев после выдачи), в `train_model.py`
достаточно заменить источник целевой переменной на них — пайплайн
парсинга и признаков не меняется.

Бэкенд — CatBoostRegressor. Если пакет `catboost` не установлен,
автоматически используется `sklearn.HistGradientBoostingRegressor` (об
этом печатается предупреждение в лог). Объяснение в `score.py`:

- с CatBoost — честные per-sample SHAP-значения через встроенный
  `model.get_feature_importance(pool, type="ShapValues")` (отдельный
  пакет `shap` не нужен);
- с sklearn-фолбэком — глобальная важность признаков модели.

## Как запустить

```bash
pip install -r requirements.txt

python src/synth_data.py       # собрать обучающий набор в data/
python src/train_model.py      # обучить модель, сохранить в model/
python src/score.py выписка.pdf              # человекочитаемый отчёт
python src/score.py выписка.pdf --json       # полный результат в JSON
python src/score.py выписка.pdf --server     # компактный пейлоад для сервера
```

Компактный пейлоад (`--server`) — то, что имеет смысл хранить и
передавать дальше по системе:

```json
{
  "final_score": 8.4,
  "ai_comment": "Коэффициенты слоя 3:\n×0.5 Регулярность дохода (income_cv) — ..."
}
```

Программно:

```python
from score import score_statement, score_statement_for_server

result = score_statement("выписка.pdf")
result["final_score"]      # 0..25
result["final_verdict"]    # текстовый вердикт
result["rule_based_factors"]   # разбивка по коэффициентам с объяснением
result["model_explanation"]    # вклад признаков по версии модели

# либо сразу компактно, для отправки на сервер:
payload = score_statement_for_server("выписка.pdf")
# {"final_score": ..., "ai_comment": ...}
```

`score_statement` — единственная функция, которую нужно вызывать при
встраивании модуля в основной сервис; `score_statement_for_server` —
её обёртка, если нужен сразу минимальный пейлоад без промежуточных
данных.

## Ограничения

- **Формат парсера рассчитан на конкретный шаблон выписки**
  («Индивидуальная выписка по платёжному счёту», Сбербанк). Другой банк
  печатает выписку иначе — под него нужен свой `_HEADER_RE`/`_DETAIL_RE`
  либо отдельный парсер. `validate_against_declared_totals()` — это
  обязательная проверка при добавлении нового формата: если контрольные
  суммы не сошлись, часть операций не распарсилась.
- **`estimated_monthly_debt_payment` — эвристика.** Регулярный платёж
  физлицу (например, аренда или алименты) с низким разбросом суммы
  может ошибочно попасть в «похоже на кредит», если тот же контрагент
  встречается ≥3 раз. Ключевые слова (`DEBT_PAYEE_KEYWORDS`) снижают
  этот риск, но не убирают полностью.
- **Целевая переменная модели пока формульная, не наблюдаемая.** Пороги
  и коэффициенты в `scoring_rules.py` заданы явно и совпадают с
  анкетной методикой там, где признак и вопрос анкеты измеряют одно и
  то же; при накоплении реальных данных о результатах выдачи кредитов
  модель нужно переобучить на них.
- Диапазоны признаков в `synth_data.py` привязаны к периоду выписки
  ~90 дней; при выписках на другой срок счётчики операций
  (`*_tx_count`, `tx_per_month`) нужно пересчитать под соответствующий
  масштаб.
