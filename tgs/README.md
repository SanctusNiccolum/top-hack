# Модуль альтернативного скоринга по Telegram-каналу

Считает дельту кредитного рейтинга (**−25…+25**), уровень риска и
объяснение для пользователя по его сообщениям за 90 дней.

```bash
pip install -r requirements.txt
cp .env.example .env             # впиши GIGACHAT_AUTH_KEY
python -m tg_scoring.cli check   # диагностика подключения
python -m tg_scoring.cli run data/sample_input.json -o out.json
```

## Главный принцип

**LLM не ставит баллов.** GigaChat работает экстрактором фактов: возвращает
категорию, дословную цитату, уверенность и модальность. Всю арифметику
делает детерминированный код.

Это не стилистическое предпочтение, а три конкретных свойства:
воспроизводимость между запусками, возможность перетюнить веса без
переписывания промпта и объяснимость перед тем, кто спросит «почему
именно −6.4».

```
Telegram → конвертер → очистка → пре-фильтр → чанки
                                                │
                                          GigaChat (сигналы)
                                                │
                                    валидация → агрегатор → ответ
```

## Формула

```
signal_eff = confidence × modality
n_eff(c)   = Σ signal_eff по категории
sat(c)     = 1 − exp(−n_eff / 3)
delta_raw  = Σ weight(c) × sat(c)
delta      = 25 × tanh(delta_raw / 20) × min(1, √(N_clean / 150))
```

`modality`: факт 1.0, намерение 0.4, гипотеза 0.15, шутка или цитата 0.

Три вещи, которые тут делают всю работу:

**Насыщение.** Без него сорок упоминаний работы дают +320, и человек,
который просто много пишет, автоматически упирается в потолок.

**Штраф за покрытие.** Человек с пятнадцатью сообщениями не должен
получать ±25 — доверять там нечему. Ниже 10 сообщений модуль возвращает
`insufficient_data` и не гадает.

**Риск считается отдельно от дельты.** Стабильная работа плюс еженедельные
ставки дают почти нулевую дельту, но риск обязан остаться видимым — банку
нужно именно это, а не усреднённая цифра.

Времени в формуле нет: окно и так 90 дней, а экспоненциальный спад внутри
него давал разброс 1.0 → 0.37 — «уволили в начале окна» весило втрое
меньше «уволили вчера», хотя для кредитного решения это события одного
порядка.

Все параметры читаются из `.env`, править код не нужно. Как подбирать —
в [RUNNING.md](RUNNING.md).

## Защита от накрутки

Пользователь **знает**, что его канал анализируют ради кредита, поэтому
попытка накрутки — не гипотеза, а ожидаемое поведение. Четыре слоя:

1. Угловые скобки вычищаются из текста на этапе очистки — разметку чанка
   в промпте сломать нельзя (`</msg>` не сработает).
2. Каждое сообщение в своём теге с id: инструкция из одного сообщения не
   протекает на весь чанк.
3. В промпте явно сказано, что блок `<messages>` — данные, не команды.
4. **Валидатор:** категория из закрытого списка, `message_id` из состава
   чанка, `quote` — дословная подстрока текста сообщения.

Четвёртый слой самый результативный: модель, которая придумала сигнал,
почти никогда не может подкрепить его дословной цитатой. Тест
`test_injection_does_not_move_the_score` проверяет крайний случай —
полностью скомпрометированный провайдер выдаёт максимум по всем
сообщениям, дельта остаётся ровно 0.0.

Отрицание обнуляет сигнал, а не инвертирует: отсутствие порока не
заслуга, а плюс за «не играю в казино» — тривиальная накрутка.

## Комплаенс

14 категорий, из них 7 позитивных и 7 негативных; три
(`gambling`, `debt_distress`, `microloan_reliance`) участвуют в расчёте
уровня риска. Полный список — в `categories.py`.

Там же `DENIED_TOPICS` — восемь тем, по которым модель обязана не создавать
сигналов: здоровье, религия, национальность, политика, сексуальная
ориентация, семейное положение, судимость, членство в организациях.

Это не перестраховка, а 152-ФЗ: перечисленное относится к специальным
категориям персональных данных, для обработки которых согласия на парсинг
канала недостаточно. Список попадает в промпт автоматически, а всё, что
модель всё-таки вернула вне разрешённого перечня, отсекает валидатор.

Тонкая грань, которую стоит проговорить заранее: **лудомания — это
здоровье, а траты на ставки — финансовое поведение.** Модуль фиксирует
факт трат и их регулярность, а не ставит диагноз. Формулировки в ответе
соответствующие: «регулярные упоминания ставок», но не «признаки игровой
зависимости».

PII маскируется **до** отправки во внешний API: телефоны, карты (с
проверкой Луна), почта, СНИЛС, счета, документы. ФИО и адреса — через NER,
если включить `PII_USE_NER=true`.

Цитаты сообщений в ответ не попадают: наружу идут только категории и
агрегаты, цитаты остаются во внутреннем логе.

## Очистка

Порог «выкидываем короткие сообщения» здесь сознательно **не**
используется. «Уволили.» — восемь символов и сильнейший негативный сигнал,
«Оффер!» — шесть. Сильные жизненные факты пишут коротко, длинно пишут
рассуждения. Вместо длины — фильтр информативности: короткое сообщение с
маркером сохраняется всегда.

Отдельно отсеивается технический вывод: логи сборки, консоль, SQL,
стектрейсы. Дело не в токенах — в реальной выгрузке путь
`D:\Моя папка\учёба\УрФУ\...` внутри вывода `docker build` срабатывал как
маркер «активная учёба», то есть человек получал плюс к рейтингу за
название папки.

Ссылки заменяются на `<link:домен>` с сохранением домена: `1xbet.ru` —
прямой сигнал, а вырезанная целиком ссылка его уничтожает. Путь и query
выбрасываются, там реферальные id.

Дедупликация — MinHash + LSH по символьным шинглам без пунктуации: точное
сравнение не свяжет «слил всё на ставках» и «опять проиграл в бк», хотя
это одно событие, описанное дважды.

Что делать **не** надо, и код этого не делает: резать мат и сленг,
лемматизировать, стеммить. Для LLM нормализованный текст читается хуже
исходного.

## Пре-фильтр

Отправлять в LLM всё не нужно и вредно: чем больше нейтрального шума в
чанке, тем чаще модель выдумывает сигнал, лишь бы не вернуть пустой ответ.

Ступень 0 — словарь из ~300 паттернов плюс случайная контрольная выборка
10%. Контрольная выборка нужна не для полноты, а для **измеримости**:
сигналы, которые LLM находит в этих 10%, — прямая оценка того, чего
недобирает словарь.

```bash
python -m tg_scoring.cli prefilter-report data/sample_input.json
```

Векторный слой (`VectorPrefilter`) заложен, реализация на
sentence-transformers написана, по умолчанию выключена. Объединение с
лексикой через `OR`, а не `AND`; прототипы — реальные фразы, а не названия
категорий; сравнение — max-similarity к прототипам, не к центроиду.
Включать имеет смысл, когда появится размеченная выборка, на которой можно
измерить пользу.

## Форматы входа

Модуль принимает свой контракт (`AnalyzeRequest`), а `run` определяет
формат сам:

| В файле | Что это |
|---|---|
| `texts` | плоский `{user_id, texts}` от бэкенда |
| `request_id` + `messages` | готовый вход модуля |
| `messages` без `request_id` | выгрузка Telegram Desktop |

Конвертеры доступны и по отдельности: `from-backend`, `from-telegram`.

## Известные ограничения

Стоит знать до того, как о них спросят.

- **Веса экспертные, не откалиброваны на данных.** Нет золотой выборки,
  precision/recall по категориям не измерены. Это первое, что надо сделать
  дальше: 250–300 размеченных вручную сообщений.
- **Свежесть сигнала не учитывается** — событие в начале окна весит
  столько же, сколько вчерашнее. Осознанное решение для 90 дней, но при
  расширении окна его надо пересмотреть.
- **Сарказм и ирония распознаются плохо.** Частично закрыто модальностью
  `quote_or_joke`, но не полностью.
- **Только текст.** Голосовые, картинки и видео игнорируются.
- **Пре-фильтр может пропустить перефразированный сигнал** без маркерных
  слов — ради этого случая заложен векторный слой.
- **Качество зависит от атрибуции на стороне бэкенда.** Если в выгрузку
  попадут чужие сообщения или пересланные посты, модуль отнесёт их
  пользователю; единственной защитой останется поле `about_author`,
  которое проставляет модель.
