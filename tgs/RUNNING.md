# Как гонять модуль

Сразу к главному: **очистка автоматическая.** Она внутри пайплайна и
выполняется всегда — при `run`, при `analyze`, при вызове по HTTP.
Отдельным шагом чистить ничего не надо.

---

## Одна команда

```powershell
.venv\Scripts\activate
python -m tg_scoring.cli run data\backend_sample.json -o out\user1.json
```

Формат определяется сам:

| В файле есть | Что это |
|---|---|
| `texts` | payload бэкенда `{user_id, texts}` |
| `request_id` + `messages` | готовый вход модуля |
| `messages` без `request_id` | выгрузка Telegram Desktop |

Папки под результат создаются сами. Сводка печатается **до** записи файла,
и если запись почему-то не прошла — полный JSON уходит в stdout: анализ
уже оплачен, терять его из-за файловой мелочи незачем.

```
──────────────────────────────────────────────
РЕЗУЛЬТАТ
──────────────────────────────────────────────
  статус:        ok
  дельта:        -6.4
  риск:          medium
  уверенность:   0.78
  проанализировано: 640 (с сигналами: 27)
  факторы:
      -7.1  gambling (3)
      +4.3  employment_stable (4)
      -2.4  impulsive_spending (2)
```

## Все команды

Без ключа GigaChat работают четыре первые — на них удобно настраивать
очистку и словарь до подключения модели.

| Команда | Что делает | Ключ |
|---|---|---|
| `clean` | что осталось после очистки и что отсеялось | нет |
| `prefilter-report` | какие категории сработали, что уйдёт в LLM | нет |
| `prompt` | точный текст промпта для чанка | нет |
| `tune` | подбор строгости по сохранённым сигналам | нет |
| `from-backend` | `{user_id, texts}` → вход модуля | нет |
| `from-telegram` | `result.json` → вход модуля | нет |
| `check` | диагностика подключения по шагам | да |
| `run` | всё сразу: любой формат → результат | да |
| `analyze` | прогон готового входа модуля | да |

Запускать через `python -m tg_scoring.cli`, а не `python tg_scoring\cli.py`:
внутри пакета относительные импорты, при прямом запуске файла они
отвалятся.

---

## Что происходит внутри

1. **Конвертация** — в контракт модуля, id по позиции.
2. **Очистка** — служебные сообщения, технический вывод, нормализация,
   ссылки, PII, обрезка длинных, фильтр информативности, дедупликация.
3. **Пре-фильтр** — словарь маркеров плюс случайные 10%.
4. **Чанкинг** — по 40 сообщений.
5. **GigaChat** — чанк за чанком, при кривом JSON один ретрай с
   repair-промптом.
6. **Валидация** — отсев галлюцинаций.
7. **Агрегация** — веса, насыщение, coverage, риск.
8. **Объяснение** — шаблонный текст по топ-факторам.

Шаги 2 и 3 — это и есть «почистить».

## Пошагово для нового пользователя

```powershell
python -m tg_scoring.cli clean data\backend_sample.json          # глянуть
python -m tg_scoring.cli run   data\backend_sample.json -o out\user1.json
```

На знакомом источнике первый шаг можно пропускать. На новом — не стоит:
на чужой выгрузке регулярно вылезает то, чего в синтетике не было, и
увидеть это до траты токенов дешевле.

Если что-то идёт не так — `--verbose`, пайплайн логирует каждый этап с
цифрами.

---

## Когда что-то не так

### `insufficient_data`

Не ошибка, а защита: после очистки осталось меньше 10 сообщений. Смотри
строку «проанализировано». Если там мало — дело не в модуле, а в объёме
данных; проверь `clean`, возможно очистка выбросила больше, чем ты ожидал.

### Статус `ok`, но дельта почти нулевая

Готовая дельта умножается на `coverage = min(1, √(N / 150))` — штраф за
малый объём. При десяти сообщениях это множитель 0.26.

| Сообщений | `COVERAGE_TARGET_MESSAGES=150` | `=25` |
|---:|---:|---:|
| 10 | −2.2 | −5.4 |
| 17 | −2.9 | −7.0 |
| 25 | −3.5 | −8.5 |
| 60 | −5.4 | −8.5 |
| 150 | −8.5 | −8.5 |

Один и тот же профиль сигналов. Для тестов на коротких файлах:

```
MIN_MESSAGES_FOR_VERDICT=10
COVERAGE_TARGET_MESSAGES=25
```

**Перед защитой верни 150.** Множитель существует затем, чтобы человек с
двумя десятками сообщений не получал те же ±25, что человек с шестьюстами.

### Сигналов почти нет

Дельта вроде −0.25 чаще означает не мягкую шкалу, а то, что до агрегатора
доехало полтора сигнала. Смотри `meta.signals_rejected`:

| Причина | Что значит |
|---|---|
| `quote_mismatch` | модель перефразирует вместо цитирования — проблема промпта |
| `low_confidence` | модель не уверена; можно понизить пороги |
| `not_about_author` | в выгрузке чужие сообщения |
| `forwarded` | пересланные посты; проверь фильтр на стороне бэкенда |
| `denied_or_unknown_category` | модель лезет в запрещённые темы |

Крутить веса, пока тут десятки отказов, бесполезно — сделаешь громче то,
чего нет.

### GigaChat не отвечает

```powershell
python -m tg_scoring.cli check
```

Идёт по шагам: токен → список моделей → тестовая генерация, и печатает
подсказку под конкретную ошибку. Подробности — в
[SETUP_GIGACHAT.md](SETUP_GIGACHAT.md).

## Калибровка строгости

Разметка стоит токенов, арифметика — нет. Сохрани сигналы один раз:

```powershell
python -m tg_scoring.cli run data\user1.json -o out\user1.json --dump-signals sig.json
```

Дальше крути сколько угодно, LLM не вызывается:

```powershell
python -m tg_scoring.cli tune sig.json --messages 150
```

```
           k=3.0     k=2.0
  scale=20.0    -9.2    -11.4
  scale=15.0   -11.9    -14.4
  scale=12.0   -14.2    -16.9
  scale=10.0   -16.3    -18.9
  scale=8.0    -18.7    -21.1
```

Выбрал клетку — прописал в `.env` — перезапустил.

### Ручки, по порядку

**`TANH_SCALE`** (20) — главная. `delta = 25 × tanh(сырая_сумма / scale)`.
Меньше — круче кривая, та же разметка даёт большую дельту. Пропорции между
категориями при этом не едут, меняется общий масштаб. 12 — заметно строже,
8 — очень строго.

**`SATURATION_K`** (3) — как быстро категория набирает полный вес. Меньше —
хватает меньшего числа упоминаний. Трогать после первой.

**`MIN_CONFIDENCE_POSITIVE`** (0.6) / **`MIN_CONFIDENCE_NEGATIVE`** (0.7) —
сколько сигналов вообще принимается. Понижение даёт объём вместе с ложными
срабатываниями. Негативный порог выше намеренно: ложный минус бьёт по
человеку сильнее ложного плюса, и ослаблять его стоит последним.

**Веса категорий** в `categories.py` — если строже надо не вообще, а
точечно.
